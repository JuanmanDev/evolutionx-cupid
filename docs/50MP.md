# Real 50 MP on the Xiaomi 12 (cupid) — and why GCam can't

Everything here was **measured on the device**, not assumed. Where a widely
repeated belief does not hold on this model, it is called out. *(Spanish version:
[`50MP.es.md`](50MP.es.md). Deeper technical notes: [`CAMERA-50MP.md`](CAMERA-50MP.md).)*

## TL;DR

- The main sensor is 50 MP (8192×6144, Sony IMX766 Quad-Bayer).
- **Real 50 MP works** through the **Xiaomi camera**, **Aperture**, and the
  bundled **Cam50Test** — JPEG *and* DNG.
- **GCam cannot do 50 MP on this phone.** Not a config or APK problem — it was
  taken all the way down to patching the camera framework and rebuilding
  `cameraserver`. It is a hardware/HAL wall.
- The real 50 MP has a **magenta tint** that can't be fixed in-app (missing
  crosstalk calibration). For everyday photos, GCam at 12.6 MP is usually better.

## How the real 50 MP is achieved

The HAL only produces full-size stills inside Xiaomi's proprietary path. Four
pieces are needed, and **all four** at once:

1. **Whitelisted package** — `persist.vendor.camera.privapp.list`. Outside the
   list the same session returns 1920×1440; inside it, 8192×6144.
2. **Proprietary session operating mode `0x80F3` (33011)** —
   `SESSION_OPERATION_MODE_NORMAL_ULTRA_PIXEL_PHOTOGRAPHY`, from MiuiCamera. The
   community table's `0x9004`/`36868` "50 MP mode" **does not work on cupid**
   (the HAL rejects the whole session); `0x80F5` (pro) rejects RAW too.
3. **Two streams** — a small one plus the 8192×6144 one. With only the big one,
   `onConfigureFailed`.
4. **The `xiaomi.remosaic.enabled` tag** on the capture request — this is what
   brings real resolution. Without it the HAL returns an **upscaled 12.6 MP**
   even though the file measures 8192×6144 (real-detail metric drops from 0.047
   with the tag to 0.004 without).

The framework support for all of this lives in the patched
`Camera3Device.cpp` / `CameraProviderManager.cpp` (see [`../patches/`](../patches/)):
when an app configures a JPEG output larger than the biggest still the HAL
advertises on its own, the service switches the session to `0x80F3` and tags the
request. Ordinary apps see nothing of it.

Why Xiaomi's own path is required: `IFEMaxLineWidth = 7296 < 8192`, so the ISP
cannot process that width in one pass; Xiaomi does it in strips in its offline
(MIVI) pipeline, selected by that operating mode.

## Why GCam cannot do 50 MP (the full journey)

GCam's HDR+ engine only ever asks lenses for **RAW12 / RAW_SENSOR / YUV / RAW10**,
never JPEG, and reserves 22–37 in-flight images. At 50 MP that does not hold, and
the code is closed (assembler-patched APKs), so the good path can't be added to it.

This was pushed as far as it goes:

1. **Advertise the full size** (`persist.sys.camera.qcfa_jpeg`): GCam ignores it —
   its pipeline is binned RAW burst, it outputs 12.6 MP.
2. **Old-libgcam ports (LMC 8.4)** crash on launch:
   `frame_raw_max (8192) matches neither active (4096) nor pixel array (4096)`.
   That check is *why* Quad-Bayer full-res breaks GCam.
3. **Patch the active array to 8192×6144** (rebuilt `cameraserver`,
   [`../patches/parche_active_full.py`](../patches/parche_active_full.py)):
   GCam stops crashing, reads the sensor as 8192×6144, **configures a full-size
   RAW10 stream and starts HDR+** — but the frames come back **black**.
4. **Force the remosaic mode (`0x80F3`) onto GCam's RAW stream**: the log confirms
   the session enters the Xiaomi mode with the remosaic tag set, and the RAW10 is
   still **black**, no photo saved.

**Conclusion (measured, not guessed):** the HAL's full-res mode only ever delivers
**JPEG/BLOB** remosaic'd output, never RAW10/YUV at full resolution to a
third-party stream. GCam only gets a valid 50 MP frame if it consumes BLOB, but
its HDR+ is wired to RAW, which the HAL does not fill at full size. No
framework change bridges that. **GCam 50 MP is impossible on this hardware/HAL.**

### Note: the full-size advertisement can't be left on globally

With the full RAW size visible, GCam ports pick it for the main lens and go
black (other lenses stay fine). That is why the advertisement sits behind a
property and should be shown to apps deliberately, not globally.

## The colour problem (why 50 MP looks magenta)

With `xiaomi.remosaic.enabled` the detail is real, but the image has a **magenta
tint and a fine grid**, channels around R=71 G=49 B=79 (green halved). The HAL log
says why:

    E/Remosaic: SPAF xtalk EEPROM data is invalid
    E/REMOSAIC-NODE: REMOSAIC XTALK DATA GET Err

`com.qti.node.remosaic.so` looks for `remosaic_crosstalk_data.bin` (doesn't
exist) and the module's EEPROM has no valid crosstalk data (its `CrossTalk` region
is declared with **size 0**). Without the gain map the remosaic does not relocate
pixels, so the ISP demosaics 2×2 same-colour blocks as if they were normal Bayer.
Fixing it in post with per-channel gains **does not work** (measured): it is not a
white-balance imbalance but a mis-placed pattern. Only exposure compensation
(`persist.cam50.ev -6`) helps, by taming blown highlights.

## Verifying a 50 MP photo is real

A file can say 8192×6144 and still be an upscaled 12.5 MP. Two checks that don't
lie:

- **In the RAW**, count rows with data. If only 1536 of 6144 have data, the sensor
  is being read before the remosaic even though the file measures right.
- **In the JPEG**, look at the size. A real 50 MP shot of a detailed scene is
  20–45 MB; an interpolated one is well below that.
